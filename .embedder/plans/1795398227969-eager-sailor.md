# STM32L072 / SX1276 migration plan

## Outcome

Replace the nested legacy GCC Makefile build with a root-level CMake build for the existing LGT92 LoRaWAN firmware. The user confirmed that `CMakeLists.txt` and `README.md` belong at the **repository root**, and `build/` is for generated output only—there will not be a duplicate `CMakeLists.txt` in `build/`.

## Recommended implementation

1. **Capture the current GCC build as a baseline before retiring it.** Use the existing manifest in [`Projects/Multi/Applications/LoRa/DRAGINO-LRWAN(AT)/gcc/Makefile`](Projects/Multi/Applications/LoRa/DRAGINO-LRWAN\(AT\)/gcc/Makefile#L11-L105) to verify the legacy target with its Arm GNU toolchain. Keep any failure fixes narrowly scoped to the relevant build inputs and do not edit generated HAL/initialization code.
2. **Add root CMake cross-build files.** Create `CMakeLists.txt` at the repository root and a proposed `cmake/arm-none-eabi-gcc.cmake` toolchain file. Configure C and assembly for `arm-none-eabi-gcc` and a bare-metal `Generic` target; use the established Cortex-M0+ Thumb flags, `-Os`, target definitions (`STM32L072xx`, `USE_STM32L0XX_NUCLEO`, `USE_HAL_DRIVER`, `USE_SHT`, `REGION_EU868`), and include paths from the existing Makefile. The project sources are in the nested `DRAGINO-LRWAN(AT)` application; its linker script is [`gcc/gcc-stm32l072cz.ld`](Projects/Multi/Applications/LoRa/DRAGINO-LRWAN\(AT\)/gcc/gcc-stm32l072cz.ld#L1-L7).
3. **Preserve firmware behavior while making the target specific.** Build the current application, required STM32L0 HAL/CMSIS startup/system sources, the `STM32L0xx_Nucleo` BSP, the `sx1276mb1las` and SX1276 radio driver, and LoRaWAN MAC/crypto/utilities. The legacy Makefile selects EU868; in CMake compile the EU868 dispatch set (`Region.c`, `RegionCommon.c`, `RegionEU868.c`) while retaining the other LoRaWAN source files in the repository. `Region.c` guards region dispatch with `REGION_EU868` (see [`Region.c`](Middlewares/Third_Party/Lora/Mac/region/Region.c#L305-L349)); keep `lora-test.c`, which supplies LoRaWAN certification behavior used by the app. Retain app dependencies such as GPS, MPU9250, IIC, watchdog, and filter: `main.c` calls these services ([`main.c`](Projects/Multi/Applications/LoRa/DRAGINO-LRWAN\(AT\)/src/main.c#L407-L434)).
4. **Produce both firmware formats with CMake.** Link `lgt92.elf` using the existing memory script, nano/nosys specs, math library, and section garbage collection options from the Makefile; add a post-build `arm-none-eabi-objcopy` step for `lgt92.hex`. Put outputs in a fresh subdirectory such as `build/lgt92/` so the existing root and nested-app build artifacts are not overwritten during migration.
5. **Document and finish the migration.** Add root `README.md` with prerequisites and exact configure/build commands, e.g. `cmake -S . -B build/lgt92 -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi-gcc.cmake` followed by `cmake --build build/lgt92`. Update `.gitignore` for root CMake build metadata/artifacts. Once a clean CMake build succeeds, remove the obsolete `gcc/Makefile` and the app's `EWARM/` and `MDK-ARM/` project trees as requested. Remove the clearly unused app-only RF test pair `src/test_rf.c` / `inc/test_rf.h` (only declarations/definitions are referenced in the repository), and remove non-L0 app variant files only where the final reference scan confirms they are solely for retired IDE profiles. Keep shared vendor HAL/CMSIS/BSP and LoRaWAN files rather than broadly deleting vendor trees.

## Evidence and constraints

* The active GCC definition is in the nested app's `gcc/Makefile`; it selects `STM32L072xx`, `SX1276MB1LAS`, and EU868, and uses `-mcpu=cortex-m0plus -mthumb`, `-Os`, `-ffunction-sections`, `--gc-sections`, nano/nosys specs and `-lm` ([Makefile lines 21–50, 93–105, 147–170](Projects/Multi/Applications/LoRa/DRAGINO-LRWAN\(AT\)/gcc/Makefile#L21-L50)).

* The app contains alternate L1/L4 sources/configuration and IDE project directories; those are not in the GCC source list. Deletions should be limited to app-level files confirmed unused after removing those profiles.

* Existing `build/` directories contain old generated CMake objects/HEX output. They are not proof of a fresh reproducible build, so use a clean CMake build directory and preserve existing binaries until parity is checked.

* No live-device operation is part of this migration. The provided hardware inventory has no debugger probe; build and artifact checks are sufficient for this build-system change.

## Validation

1. Build the legacy GCC Makefile once before removing it; record whether it completes and its ELF/HEX size. If it fails, fix only the build-relevant inputs and retain a record of the cause.
2. Configure and build from the repository root using the README commands in a fresh CMake output directory. Require both `build/lgt92/lgt92.elf` and `build/lgt92/lgt92.hex` to be generated successfully.
3. Inspect the ELF with Arm GNU `readelf`/`size`; confirm it is an ARM Cortex-M0+ firmware image, the linker script's 192 KiB flash / 20 KiB RAM limits are respected, and the map/source list contains only the STM32L072 + SX1276MB1LAS target and the intended EU868 LoRaWAN region.
4. Compare the CMake result against the baseline for source coverage and firmware section sizes, then run a second clean CMake configure/build to ensure the README workflow is reproducible. Do not flash hardware.
